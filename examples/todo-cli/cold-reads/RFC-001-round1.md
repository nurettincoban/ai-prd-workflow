# Cold read: RFC-001 Storage core

Question: what would I have to guess to implement this?

## 1. Guesses that change observable behavior or a shared interface

1. `TdError` signature is not given. "carries `message` and `exit_code` (default 1)" does not say whether the constructor is `TdError(message, exit_code=1)`, or whether `str(e)` equals `message`. RFC-002 needs exit code 2 for usage errors (CLI-1, CLI-2, OUT-2). No usage-error subclass is defined, although "or a subclass" implies one. RFC-002 will have to guess how to raise it.
2. Missing task-mutation functions. Only `add_task` is specified. There is no `remove_task`, `mark_done` or `clear_done`, and no lookup that raises on an unknown id. Criterion 8 removes a task "by filtering the list" in the test itself. The interface "names are fixed so RFC-002 to RFC-004 can use them" is incomplete for `done`, `rm` and `clear`. Validation of `add` text (empty text, newline; CLI-1) is also unplaced. `add_task` as specified accepts anything.
3. `resolve_path()` return type is `pathlib.Path`, but criterion 1 says it "returns `/x/y.json`". A `Path` does not equal a `str`. For a relative value, "accepted as given" does not say whether it is made absolute, or relative to which cwd. CLI-7 says `TD_FILE` is "read once, at startup", but `resolve_path()` reads the environment on every call (the tests depend on that). Which one wins is a guess.
4. Argument types are unspecified. Does `load_store` / `save_store` take `str`, `Path`, or both? The RFC never says. Neither is it stated whether `save_store` validates the store it is given. A caller could write a file that `load_store` then calls corrupt.
5. Order of checks in `load_store`. Criterion 4 says a missing file returns the empty store. Criterion 3 says a missing parent directory raises. A missing parent also means a missing file, so the two collide unless the parent is checked first. The RFC does not say so. Other I/O failures are also unspecified: the path is a directory, the parent is a regular file, permission denied, invalid UTF-8 bytes, a 0-byte file. "all failures are `TdError`" suggests they are wrapped, but whether a `UnicodeDecodeError` is "corrupt" is a guess.
6. "Message names the path." The path as passed in, the expanded path, or the realpath? This matters on macOS, where the temp dir is a symlink, and for symlinked targets. Criterion 6 tests `message contains the file path`.
7. Validity gaps in "corrupt". These are the cases the definition leaves open:
   - `version` of 0, negative, `true` (`True == 1` in Python), or a non-int.
   - A negative or zero `next_id` or task id. `next_id: -5` with `tasks: []` passes "greater than every id".
   - `tasks` not a list.
   - A task `text` that is not a `str`. The sentence lists wrong types in general, but the criterion 6 list never tests `text`.
   - Newlines or control characters inside stored `text`. Is that valid, or corrupt? OUT-4 says printing strips them, so it is valid.
8. File permissions. The save algorithm says "create temp file in dir". The usual call, `mkstemp`, creates mode 0600 and then `os.replace` leaves the data file 0600 whatever the old mode was. SEC-3 requires "default umask permissions, no chmod". The RFC's "implementer's choice" list does not include permissions. It is also unspecified whether an existing file's mode is preserved.
9. What `save_store` does when the failure is after `os.replace`. This covers a directory fsync that raises something other than `OSError`. It is unspecified whether the call raises, whether the error is wrapped in `TdError`, and what the caller sees. Criterion 12 says "no other error is swallowed". Criterion 10 and "all failures are TdError" imply that OSErrors from the write path become `TdError`. Whether a raw `OSError` or `TdError` is expected is a guess. This is observable through exit code and message in RFC-002. The same gap exists for `open(dir)` itself raising `PermissionError` (an `OSError`, so skipped?) versus "no handle" on Windows.
10. First save when no previous file exists. Criterion 9 requires the target to be "parseable and equal to the previous store". On a first write there is no previous file, so an interruption before `os.replace` leaves no target. The expected result for that case is a guess.
11. Module-level behavior of `td`. ARCH-1 needs the shebang and executable bit, and ARCH-2 needs `main`. The RFC says only "library-style functions" and "No command exists yet". Whether to add the shebang and a `__main__` guard now is a guess. Importing the extensionless file via `SourceFileLoader` must not run anything. The module name the loader uses is unspecified.
12. `tests/` layout. Whether `tests/__init__.py` is needed. With `discover tests`, `helpers` imports as a top-level name only if tests do `import helpers`. The RFC does not say which form. How helpers.py locates `td` is not stated (probably "parent of tests/"). Whether the temp-dir helper restores `TD_FILE` afterwards is also left open.

## 2. Contradictions

1. NAME-3 versus criterion 2 versus DEV-4. NAME-3 says the strings appear "nowhere else in the code as string literals". Criterion 2 permits "comments" only. DEV-4 requires one-line docstrings on public functions. A docstring or an error message that mentions `TD_FILE` is a string literal, and it fails criterion 2. The RFC does not say whether docstrings and messages count.
2. SEC-3 (default umask, no widening) versus the temp-file step. The RFC's pseudocode implies mkstemp-style 0600 files. See item 1.8. The RFC gives no resolution.
3. TEST-3 is listed in the RFC's Rules but cannot be met here. It says to run "each command including `add`", and no command exists in this RFC. Criterion 6 covers only `load_store`. SAFE-3 ("every command, including `add`") is likewise only partly covered. The RFC does not hand the rest to RFC-002 explicitly.
4. F1's criterion says the missing-parent error is "exit 1, message on stderr". The RFC has no stderr output, only `TdError`. F15 says "core commands pass the test suite on macOS and Linux", and F3 and F4 say commands exit non-zero. None of these can be satisfied by an RFC with no commands. F15 is claimed as a covered feature, yet no criterion in this RFC tests platform behavior. The only platform item is the skipped directory fsync, which criterion 12 tests with an injected `OSError`, not on a real platform.
5. The Summary says the RFC settles F-3 (fsync), "never leaving a partial file". But the Implementation considerations say overlapping runs can lose a task and no lock is added. This is consistent with F17 and G2 only if G2 is reworded, which both FEATURES and RULES flag as unresolved. The RFC cites `RFCS.md Open conflicts` and `PRD-REVIEW.md`, and neither was provided, so I cannot verify them.
6. `version` greater than 1 is corrupt (RFC, DATA-6). F5 and DATA-6 also say "a file written by an earlier v1 build must still load". With only version 1 existing, the interaction with a future v1 build that adds fields is undefined. DATA-2 and criterion 6 say extra task fields are corrupt, so any added field would break loading. Related: DATA-1 says "version integer", and the RFC's treatment of version 0 is not defined (see 1.7).

## 3. Acceptance criteria a test cannot check, or that pass by luck

1. Criterion 9 (kill at each step). "Killing a real subprocess at each step" needs a deterministic pause or hook point per step. None is specified. Without one, a kill by timing lands wherever it lands, and the test passes by luck, for example when it is killed before the temp file exists. The injection mechanism is also unspecified. If a test patches `os.replace` or `os.fsync`, the code must call them as `os.replace` and `os.fsync` and not as `from os import replace`. The "steps" are not enumerated (write, flush, fsync tmp, replace, fsync dir). A power-loss test is impossible, so durability itself is untestable.
2. Criterion 9 also does not require that the old store is intact when the failure is injected on a real filesystem with a symlinked target or on a first save (see 1.10).
3. Criterion 12 (fsync). It says `save_store` "calls `fsync` on the temp file and on the containing directory". A test can check that both calls happened, but not the order. A directory fsync done before `os.replace` would pass, and it defeats the purpose (SAFE-2 says after). It does not say that fsync of the temp file occurs before the replace either.
4. Criterion 6 "a description of the problem". This is not checkable beyond "message is non-empty". F4 demands "the parse error". Any non-empty text passes. The checks listed also omit cases the corrupt definition names: a task with a missing or extra key, `text` not a string, `tasks` not a list, `version` boolean, `next_id` as a boolean. An implementation that skips them passes every listed case. "File byte-for-byte unchanged" passes trivially because `load_store` never writes.
5. Criterion 7. The fixture `tests/fixtures/v1.json` is written by the same author, with unspecified contents (number of tasks, non-ASCII, done flags), and nothing says to assert on what it loads to. As written it is a tautology: it detects a later change only if someone edits the fixture to match. No older build exists to prove "stays readable".
6. Criterion 8. The test does the removal itself by filtering, so it checks `add_task` only. It does not check `next_id` was incremented in the store, that `add_task` mutates in place, or that the counter survives a `save_store` / `load_store` round trip. Passing it does not show FR-6 or TEST-4 (which needs remove then add through commands).
7. Criterion 1. The default case needs `HOME` set for the test, otherwise it reads the real home directory. The test depends on `expanduser` behavior per platform. `TD_FILE` unset versus empty needs the test to delete and restore the variable, and the helper's cleanup is not specified (see 1.12). The Path versus string equality question (1.3) decides whether the assertion even compares equal.
8. Criterion 13 ("no test touches `~/.td.json`") cannot be checked by a test. Only a review can verify it. It passes by luck: a test that forgets `TD_FILE` and only reads would still pass, and nothing detects it. Any test that calls `resolve_path()` with the variable unset (criterion 1) is a near-miss.
9. Criterion 10 ("no temp file remains"). Temp file naming is the implementer's choice, so a test must compare directory listings before and after. A real killed subprocess (criterion 9) necessarily leaves a temp file, and the RFC does not say that is acceptable apart from SAFE-5's "never read as data". No criterion checks the claim that a stale temp is ignored.
10. Criterion 11 (symlink). It covers one symlink to a file in another or the same directory. It does not cover a relative symlink, a chain, or a dangling one. Symlinks are not creatable on unprivileged Windows (Windows is untested, so this is only a skip-or-fail question for the test).
11. Criterion 14. "using only the standard library" is a review check. The 3.10 floor (STACK-2, F13: "a test run on 3.10 passes") is not part of any criterion here, and it cannot be run where the observed interpreter is 3.13. A 3.11+ feature would pass criterion 14 locally.
12. Criterion 2 is a grep-style check. How the "defined once" check is run is unspecified. It is a test only if someone writes a source-scanning test, and the comment exception makes the pattern ambiguous (see 2.1).
