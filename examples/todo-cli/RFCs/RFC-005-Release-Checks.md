# RFC-005: Release checks (stdlib only, single-file install, platforms, speed)

**Features**: F13, F14, F15, F16
**Depends on**: RFC-001, RFC-002, RFC-003
**Rules**: STACK-1, STACK-2, STACK-3, STACK-4, ARCH-1, SEC-1, SEC-2, PERF-2, TEST-8, TEST-9
**Complexity**: Medium

## Summary

The constraints that are properties of the whole program, checked by tests and one manual release run once the commands exist. Nothing here adds behavior; it adds checks on the code and the release. It needs `add`, `list`, `done` and `rm` (RFC-003), the data file layout and `tests/helpers.py` (`temp_env`, `load_td`) and `DEFAULT_FILE` (RFC-001), and the line format (RFC-002), so it declares all three; it does not need `clear` (RFC-004), and none of its criteria mention it.

## Technical approach

One test module `tests/test_release.py`. It parses `td` with `ast` and inspects imports and calls; it runs `td` as a real subprocess for the install, fixture and speed checks. The line format and commands are those of RFC-002 and RFC-003 (`format_task`: `<id> [ ] <text>`). Data files the tests generate use RFC-001's layout: an object with `version` 1, `next_id` and `tasks`, each task `{"id", "text", "done"}`. The fixture is `tests/fixtures/v1.json` from RFC-001 criterion 7 (tasks 1 done "first", 3 open "naïve café", 4 done "x"; `next_id` 5). The Python 3.10 and macOS runs cannot be automated from a single machine, so they are manual steps recorded in `## Implementation Notes` of this RFC (the implementer adds that section when recording; it does not exist yet).

## Acceptance criteria

1. Every top-level module name imported by `td` (for `import a.b` and `from a.b import c`, the name `a`) is in `sys.stdlib_module_names`. Every import in `tests/*.py` is either in `sys.stdlib_module_names` or the name of a file `tests/<name>.py` (only `helpers`), and no file in `tests/` has a stdlib module's name (so a local `json.py` cannot shadow one); `td` itself is loaded by path through `importlib`, not imported by name. (F13, STACK-1, STACK-4)
2. `td` imports none of `socket`, `ssl`, `http`, `urllib`, `ftplib`, `smtplib`, `xmlrpc`, `asyncio`, `subprocess`, `pickle`, `importlib`, `ctypes`, `threading`, `multiprocessing`, and contains no reference to `system`, `popen`, `eval`, `exec` or `__import__` as a name or attribute (a call, an alias such as `from os import system as s`, or a bare reference), and no string constant equal to one of those five names (which would catch `getattr(os, "system")`). The ban on `subprocess` and on threads is stricter than SEC-2 and PERF-2 (assumption: `td` has no reason to spawn processes or threads); it applies to `td` only, not to tests. (F16, STACK-3, SEC-1, SEC-2, PERF-2)
3. Install check (every subprocess in criteria 3 to 5 gets one `env` dict copied from `os.environ` with `TD_FILE` set, `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` so the host locale cannot change the output, and `PATH` as described here; the same dict is passed to `subprocess`, so the bare name `td` is looked up on that `PATH`): the file `td` alone is copied into an empty temp directory, marked executable, and that directory is put at the front of `PATH` (the original `PATH` stays after it, so `python3` still resolves); with `TD_FILE` in a temp dir, a subprocess running the bare name `td add x` prints exactly `1 [ ] x\n` on stdout and exits 0, then `td list` prints exactly `1 [ ] x\n` and exits 0. (F14, ARCH-1)
4. Fixture check: a copy of `tests/fixtures/v1.json` is used as the data file of the installed copy of `td` from criterion 3. `td list` prints exactly `1 [x] first\n3 [ ] naïve café\n4 [x] x\n`; then `td add y` prints `5 [ ] y` and the first three tasks are still equal to the fixture's in the file. This fixture is the stand-in for "a file written by an earlier v1 build" (no earlier build exists); a later build that fails this test has broken compatibility (F5, DATA-6). (F14)
5. Speed check: a data file with 5,000 tasks (ids 1 to 5000, `next_id` 5001, text of 40 characters, generated by the test) is copied fresh before every single run of `td list`, `td add x`, `td done 1` and `td rm 2` (so `done 1` and `rm 2` always change the file and take the save path); each is run as a subprocess three times with stdout captured, every run must exit 0, and the median wall time of the whole process (interpreter start included) is under 1 second. The 1 second budget and 5,000 as "a few thousand" are assumptions; this is a regression guard, not proof that no delay is perceptible, and a failure on a slow machine is reported as a failure, not skipped. (F16)
6. Nested-run check: `tests/test_release.py` runs `sys.executable -m unittest discover tests` in a subprocess with the repository root as its working directory, `HOME` set to a fresh temp dir, `TD_FILE` unset, and an environment variable that makes this nested run skip criteria 5 and 6 itself; the nested run exits 0, and afterwards the temp `HOME` contains no `.td.json`. This shows the suite passes on the current interpreter and that no test falls back to the real data file. This relies on every test that needs `HOME` or `TD_FILE` changed or unset doing it through `helpers.temp_env()`. (TEST-8, F13)
7. Syntax floor: `ast.parse(source, feature_version=(3, 10))` succeeds for `td` and every `tests/*.py` file (the JSON fixture is not parsed). It is a partial check: `feature_version` does not reject all newer syntax (for example nested same-quote f-strings), and library calls newer than 3.10 are not caught, so only criterion 8 settles the floor. (STACK-2)
8. Manual release run, recorded under `## Implementation Notes` with date, interpreter version and result: the full suite passes on Python 3.10, on at least one newer Python, on Linux and on macOS (TEST-9). These are four facts, each covered by at least one recorded run, and one run may cover two (for example 3.10 on macOS). It is not an automated test; a release is not called done until all four are recorded, but the automated criteria above do not wait for it; Python 3.10 has never been run in this project, so until then the floor is unverified. (F13, F15, TEST-9)
9. Separators: an `ast` scan of `td` finds no string constant (f-string pieces included) containing `/` or `\`, other than the value of `DEFAULT_FILE` and docstrings (so help text and messages avoid those characters, for example "or" instead of "and/or"), and no use of `os.sep`, `os.path.sep`, `os.altsep` or `os.path.altsep` (paths are built with `pathlib` or `os.path`). The directory-fsync skip is tested in RFC-001 criterion 12. (F15)

## Implementation considerations

- Windows is untested and not a release criterion (F15, PRD D-8). No Windows criterion is written.
- Implementer's choice: how timing is measured, how the 5,000-task file is generated, the name of the environment variable for the nested-run skip.

## Open Questions

1. **(assumption)** Install method is copy-to-PATH of a single file (PRD Open Question 8).
2. **(assumption)** The 1 second performance budget at 5,000 tasks; PRD gave none (NFR-7).
3. **(assumption)** `td` may not import `subprocess`, `importlib`, `ctypes` or threading modules (stricter than SEC-2/PERF-2), so the static scan cannot be bypassed by a dynamic import.
4. Python 3.10 has not been run in this environment; the floor stays unverified until criterion 8 is done.

## Implementation Notes

### Plan (written instead of waiting for confirmation: nobody confirmed any of it)

Run non-interactively, so the plan was not shown to the user and **nobody confirmed it or the assumptions below**. Predecessors RFC-001, RFC-002 and RFC-003 are Reviewed in RFCS.md, so the predecessor check passed. `reviews/REVIEW-RFC-005.md` does not exist.

- Create `tests/test_release.py` only; `td` is not changed (it already satisfies criteria 1, 2 and 9, shown by the tests passing).
- Static classes use `ast` on `td` and `tests/*.py`. Install, fixture and speed checks copy `td` alone to a temp `bin` directory and run the bare name `td` with one env dict. The nested run executes `python3 -m unittest discover tests` with a fresh `HOME`.
- Resting on unconfirmed assumptions: install is copy-to-PATH (PRD Open Question 8); 1 second budget at 5,000 tasks; the ban on `subprocess`, `importlib`, `ctypes` and thread modules in `td`; the open conflicts in RFCS.md (concurrent runs vs G2, names `TD_FILE` and `~/.td.json`, key names, line format, exit codes, `clear` built from IDEA.md) all touch what these tests assert but none changes them; RFCS.md conflicts 6 and 7 are this RFC's own assumptions.
- Implementer's choices (RFC leaves them open): timing with `time.perf_counter` around `subprocess.run`; the 5,000-task file is generated in the test; the nested-run skip variable is `TD_RELEASE_NESTED`.

### Deviations

None from the RFC. One interpretation: criterion 3 says the bare name `td` is looked up on `PATH`; the test also asserts the install directory holds only the file `td`.
