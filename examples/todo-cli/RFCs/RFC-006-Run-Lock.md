# RFC-006: Lock for concurrent runs

**Features**: F17
**Depends on**: RFC-001, RFC-002, RFC-003, RFC-004
**Rules**: SAFE-8, SAFE-1, SAFE-3, SAFE-6, STACK-1, STACK-3, DATA-7, CLI-7, PERF-1, PERF-2, OUT-2, OUT-7, TEST-1, TEST-3, TEST-5, TEST-8, DEV-1, DEV-2
**Complexity**: Medium

## Summary

Makes overlapping `td add`, `td done`, `td rm` and `td clear` runs on the same data file take turns, so no task is lost (PRD NFR-10, goal G2, decision D-9; change request CR-001). Without it, two runs read the same file, each adds its change, and the second save silently replaces the first: one task is gone. RFC-001's atomic save protects against a crash, not against this. This RFC adds the lock and one step in `main`; it changes no function, signature or acceptance criterion of RFC-001 to RFC-004, and `list` is untouched.

Depends on RFC-003 and RFC-004 because its tests run those commands. RFC-004 is a Should-have (F10); if it is skipped, the `clear` cases below are skipped with it and the rest stand. All four predecessors must be Reviewed before `/implement-rfc RFC-006` starts.

## Technical approach

Interfaces added to `td` (names are fixed; later RFCs and the tests use them):

- `LOCK_WAIT_SECONDS = 10` (assumption, PRD Open Question 19), a module-level constant read when the lock is taken, so a test can patch it.
- `MUTATING = frozenset({"add", "done", "rm", "clear"})`, module-level: the command names that take the lock. A command registered in `COMMANDS` later is read-only unless it is added here.
- `data_lock(path)`: a context manager that takes `str` or `pathlib.Path`, the same value `resolve_path` returned. It is a class with `__enter__` and `__exit__` (or any object that works in a `with` statement), not built with `contextlib`: `td` does not import `contextlib` today, and the only imports this RFC adds are `fcntl` and `time` (`time` only if `td` does not already import it).

What `data_lock(path)` does, in this order:

1. Applies RFC-001's parent check first, by the same rule `load_store` uses, so a bare filename such as `tasks.json` means the current directory exactly as it does there. The implementer may either move that check out of `load_store` into a helper that both call (a pure refactor: `load_store`'s behavior, messages and RFC-001's criteria do not change) or apply the same rule in `data_lock`; the observable rule is the same either way (see Implementation considerations). The parent directory of `path` as passed must exist and be a directory, else `TdError` with the same message form as `load_store` (`<path>: ...` starting with `str(path)`, exit 1). So a missing directory is reported the same way whether or not the lock came first, and RFC-002 criterion 8 and RFC-003 criterion 12 still hold unchanged. It does not create the directory.
2. If `fcntl` could not be imported (module-level `try: import fcntl / except ImportError: fcntl = None`), yields at once without locking (assumption, PRD Open Question 20: Windows is best effort and untested).
3. Opens the directory of `os.path.realpath(path)`, the directory `save_store` writes into, with `os.open(dir, os.O_RDONLY)` and takes `fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)`, retrying every 0.05 seconds (`time.sleep`) until `time.monotonic()` passes the deadline `LOCK_WAIT_SECONDS`. Only an error from the `flock` call itself can mean "held": `BlockingIOError` and an `OSError` whose `errno` is `EACCES` or `EAGAIN` from `flock` mean "held by someone else" and are retried (some platforms raise `EACCES` for a held non-blocking lock); an interrupted call is retried by Python itself (PEP 475). An error from `os.open` is never retried, whatever its `errno`: a mode `0o300` directory raises `EACCES` there, and that must be reported at once as a lock error (below), not wait 10 seconds and say "in use". Polling is used, not a blocking `flock`, so the wait needs no signal, alarm or thread (PERF-2, RFC-005 criterion 2). On timeout it closes the descriptor and raises `TdError` whose message starts with `str(path)` and says the data file is in use by another td run, exit 1 (assumption). Any other `OSError` from opening the directory or from `flock` (for example a filesystem that does not support `flock`, or a directory the user may write to but not read, mode `-wx`) is also a `TdError` naming `str(path)`, exit 1, with the OS error text, not a silent skip: skipping would let the run lose a task without saying so (assumption). This applies to every command in `MUTATING`, including a run that would otherwise have failed or saved fine; the only RFC-001 to RFC-004 behavior it changes is on such a directory, where the error text comes from the lock instead of `load_store` or `save_store`.
4. Yields, and on exit (normal or exception) closes the descriptor, which releases the lock. If the process is killed the operating system closes it, so a crashed run never leaves a lock behind.

Why the directory and not the data file or a `.lock` file: every save replaces the data file with a new file, so a lock on the data file would be on a file that is already gone for the next run; a `.lock` file beside it would be left behind in the data directory, where RFC-004 criterion 4 and RFC-001 criterion 10 compare directory listings exactly, and it can never safely be deleted. A directory descriptor leaves nothing behind. Cost: two data files in one directory share one lock, so they only wait for each other.

The change to `main` (RFC-002's "order of events" gains a step; RFC-002's own text says so). After step 3 (`path = resolve_path()`), if the command (`args.command`, with bare `td` meaning `list`) is in `MUTATING`, steps 4 and 5 run inside `with data_lock(path):`: `store = load_store(path)`, then the handler, which saves. The lock is released before step 6, so a slow reader on stdout cannot hold up another run (implementer's choice, no test). For commands not in `MUTATING`, nothing changes. Why not in each handler: RFC-002 passes the store already loaded to `handler(args, store, path)`, and the lock must be taken before that load, so only `main` can do it.

Which error wins, in full: argparse errors (exit 2, nothing read, no lock taken) first; then `resolve_path`; then the lock (a missing parent directory, a lock error or a lock timeout, exit 1); then `load_store` (corrupt file, exit 1); then the handler, whose own checks (RFC-003: empty text, text with a newline, a malformed id such as `abc`, an unknown id) run inside the lock. So only what argparse rejects (an unknown flag, a missing `done` id, an unknown command) gives exit 2 at once under a held lock; `td add ""` or `td done abc` against a held lock waits like any other mutating run, and then exits 2 once it has the lock (or 1 on timeout). Why: those checks live in RFC-003's handlers, after the store is loaded, and moving them out would change RFC-003.

`list` takes no lock: saves are an atomic replace, so a read sees the old complete file or the new complete file. It can therefore show a list one command behind a run that is still waiting for its turn, which is correct.

## Acceptance criteria

Every test sets `TD_FILE` through `helpers.temp_env()` (TEST-8). "Holder" means a separate subprocess that loads `td` with `helpers.load_td` equivalent code, enters `data_lock(path)`, prints `ready` and a newline on a pipe, and then waits for a line on its stdin before leaving the lock; the test reads `ready` before it starts the run under test, so no test depends on timing to get the lock held. Fixtures are written non-canonically (indented with 4 spaces). Tests of the four commands are subtests over the command.

1. `MUTATING` equals `frozenset({"add", "done", "rm", "clear"})`, `LOCK_WAIT_SECONDS` is 10, and `data_lock(path)` can be used in a `with` statement on a `str` and on a `pathlib.Path` and, while it is held, a second `data_lock` on the same directory in another process waits. (F17, SAFE-8)
2. While a holder holds the lock on the data file's directory, each of `td add x`, `td done 1`, `td rm 2` and `td clear` (run as a subprocess against a store with tasks 1 done, 2 open, 3 open) is still running after 0.5 seconds (`poll()` is `None`) and has written nothing to stdout or stderr. After the holder is released, it exits 0 within 10 seconds and the data file holds the result of that command applied to the original store. (F17, SAFE-8)
3. While a holder holds the lock, `td list` and bare `td` each exit 0 within 5 seconds with the correct stdout, and the data file is unchanged. (F17, SAFE-8)
4. Timeout: with `LOCK_WAIT_SECONDS` patched to 0.3 on the loaded module and a holder holding the lock, `main(["add", "x"])`, `main(["done", "1"])`, `main(["rm", "2"])` and `main(["clear"])` each return 1, write exactly one stderr line starting with `td:` and containing `str(path)`, write nothing to stdout, leave the data file byte for byte unchanged, and leave no other file in the directory. The call returns in under 3 seconds. (F17, SAFE-8, OUT-2, OUT-7)
5. No lost task, stress: starting from a missing data file, 8 `td add` subprocesses with different texts are started together (all spawned before any is waited for) and all exit 0; the file then holds exactly 8 tasks with the 8 texts, ids 1 to 8 each once, and `next_id` 9. This runs 5 times in a row on fresh files. (F17, G2, NFR-10)
6. No lost task, mixed commands: store with tasks 1 (done), 2 (open), 3 (open), 4 (open) and `next_id` 5; `td clear`, `td done 3`, `td rm 4` and `td add y` are started together and all exit 0. Then task 2 is present and open; task 1 and task 4 are absent; task 3 is either done or absent (it depends on whether `clear` ran after `done 3`); exactly one task has the text `y`, with id 5; `next_id` is 6; ids are distinct. Run 5 times on fresh files. (F17, G2)
7. Killed holder: a holder is killed with SIGKILL while it holds the lock (skipped unless `os.name == "posix"`); a `td add z` started afterwards exits 0 within 5 seconds and stores `z`. (F17, SAFE-8)
8. Nothing is left behind: after `td add x` (missing file), `td done 99` (missing file, exit 1), `td add -x` (exit 2), `td clear` (no done tasks) and a lock timeout (criterion 4), `os.listdir` of the data directory is exactly `["tasks.json"]` for the first and `[]` for the others on a missing file, and `["tasks.json"]` where the file existed. A missing parent directory of `TD_FILE`, and a parent that is a regular file, each give exit 1, one `td:` line starting with `td: ` and containing `str(path)`, nothing on stdout, and nothing is created. (F17, DATA-7, CLI-7, SAFE-8)
9. Where the lock sits, with a holder holding the lock (each case runs `td` as a subprocess and checks it is still running after 0.5 seconds with nothing written, then releases the holder and checks the final result): `td add x` on a corrupt data file waits and only then exits 1 with the corrupt-file message (the lock comes before the load); `td done 99` waits and then exits 1 with `no task with id 99`, file unchanged; `td add ""` waits and then exits 2, file unchanged. `td add -x` and `td done` (no id) exit 2 within 5 seconds without waiting, even though the lock is held. (F17, SAFE-8, SAFE-6)
10. Without `fcntl`: with `sys.modules["fcntl"] = None` set before loading `td`, the module loads, `main(["add", "x"])` returns 0 and stores the task. (F17, SAFE-8; assumption, Windows)
11. Lock errors: a data directory the user cannot read (mode `0o300`; skipped unless `os.name == "posix"` and the test is not running as root) makes `td add x` exit 1 with one `td:` line containing `str(path)` and the OS error text, nothing on stdout, data file unchanged. (F17, SAFE-8, OUT-2)
12. The rest of the suite passes unchanged: every criterion of RFC-001 to RFC-005, including RFC-002's `list` criteria (`list` takes no lock) and RFC-005's import, ban-list and separator checks, which now see `fcntl` and `time` in `td`. They pass without editing RFC-005 (see Implementation considerations). (F17, SAFE-8)

## Implementation considerations

- Third-party dependencies: none. `fcntl` and `time` are standard library (STACK-1); no network, no threads, no subprocess in `td` (STACK-3, PERF-2). The holder in the tests is a subprocess of the test, which RFC-005 criterion 2 allows (it bans these in `td`, not in tests).
- This RFC edits `main` in `td`, which RFC-002 owns; it adds `data_lock`, `MUTATING`, `LOCK_WAIT_SECONDS` and the `fcntl`/`time` imports. It does not touch `load_store`, `save_store`, any handler or `COMMANDS`.
- RFC-005 needs no edit (checked against `RFCs/RFC-005-Release-Checks.md`): criterion 1 accepts any name in `sys.stdlib_module_names` and `fcntl` and `time` are in it; criterion 2 is a ban list (`socket`, `subprocess`, `threading` and the like, and the names `system`, `popen`, `eval`, `exec`, `__import__`) that contains neither and that this RFC's code does not use; criterion 7 parses at the 3.10 floor, which this code meets. Two constraints this RFC must respect in `td`, because RFC-005 criterion 9 scans every string constant: no string in the new code (the timeout and lock error messages included) may contain `/` or `\`, and `os.sep` and its relatives are not used. RFC-005 criteria 3 to 5 run `td` as a subprocess and gain only the lock call, well inside the 1 second budget. The lock adds no edit to RFC-005 and is not in its scope.
- The parent check: the observable rule is RFC-001's (a bare filename means the current directory; a missing parent, a parent that is a regular file, or a path whose parent cannot be a directory is an error; the directory is never created). The message is pinned only as starting with `str(path)` after `td: `; its wording beyond that, and whether `data_lock` and `load_store` share a helper, are the implementer's choice.
- On macOS `flock` works on a directory descriptor as on Linux; this is untested here (RFC-005 criterion 8 covers a macOS run of the whole suite once it is recorded).
- Local disk only: `flock` on a network filesystem may not be honoured; PRD D-6 says one machine.
- Implementer's choice (from cold read rounds 1 and 2, no test depends on them): the poll interval, the wording of the timeout message beyond the pinned start, the names of the test holder script and helper, whether `time` is imported by name or as a module if `td` already imports it, which directory is locked when `TD_FILE` is a symlink into another directory (the realpath directory, as `save_store` writes there; the tests use `data_lock(path)` with one value, so they do not tell the readings apart), and the exact OS error text in a lock error, what `__enter__` returns, and whether the parent check is a shared helper.

## Open Questions

The wait limit and the missing lock on Windows are listed in PRD.md (Open Questions 19 and 20) and are not copied here. Assumptions this RFC adds:

1. **(assumption)** The wait is a poll of `LOCK_NB` every 0.05 seconds, not a blocking `flock`, so that no signal or thread is needed.
2. **(assumption)** A filesystem or platform error from opening the directory or calling `flock` (other than "already locked") fails the run with exit 1 instead of skipping the lock, because skipping would break G2 without saying so. Platforms with no `fcntl` at all are the one exception (PRD Open Question 20).
3. **(assumption)** The lock is released before the output is written.
4. **(assumption)** Validation inside a handler (empty text, a newline, a malformed id) happens under the lock, so it waits like any mutating run; only argparse errors skip the lock (cold read round 1, guess 1).
5. The decision to have a lock at all was made by the person running the example, not by the user (PRD D-9); if the user chooses to reword G2 instead, this RFC is retired.
