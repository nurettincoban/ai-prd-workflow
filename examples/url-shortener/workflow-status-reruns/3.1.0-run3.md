## 5. Inconsistencies

**From trace-check (FAIL):**
- **F7 (Must Have) is not assigned to any RFC.** F7 is "REST API for all URL operations … rate limiting (100 req/min/IP)" (`FEATURES.md`, API & Infrastructure). No RFC implements rate limiting, even though `PRD.md` (API, "Rate limiting: 100 requests per minute per IP") and `RULES.md` (API Standards, Security: "Rate limit all API endpoints") both require it.
- **The RFCs exist, but the `RFCS.md` index does not.** Without it, nothing records the RFC order, the deferred features or the Status column that `/implement-rfc` and `/review-rfc` keep up to date.

**From trace-check (WARN):**
- `PRD.md` has no requirement IDs (FR-n / NFR-n), so coverage from the PRD to the features cannot be checked.
- `RULES.md` rules have no IDs, so RFCs, reviews and change requests cannot cite them.
- F14 (OpenAPI/Swagger docs) and F15 (list all URLs) are not assigned to any RFC, and no `RFCS.md` defers them.

**Found by reading the documents:**
- **F15 is partly in RFC-001 without being declared.** `RFCs/RFC-001-Core-URL-Shortening.md` lists `GET /api/urls - List all URLs (paginated)` under API Endpoints, but its Features line (F1, F2, F4, F8) and its acceptance criteria leave F15 out. Either claim F15 or remove the endpoint.
- **The alias character set disagrees.** `PRD.md` and F9 in `FEATURES.md` say aliases are "3-30 alphanumeric characters". `RFCs/RFC-003-Custom-Aliases-And-Expiration.md` allows hyphens too (`^[a-zA-Z0-9-]{3,30}$`), but its acceptance criterion still says "alphanumeric".
- **Permanent redirects conflict with click tracking.** `PRD.md` and F2/RFC-001 specify HTTP 301. Browsers cache a 301, so repeat visits never reach the server. That works against F3 ("every redirect"), RFC-002's first acceptance criterion and the PRD success metric "Zero data loss on click tracking". A 302/307 would avoid this. Decide before RFC-001 is built.
- **Fire-and-forget tracking conflicts with "zero data loss".** RFC-002 records clicks "async fire-and-forget", and `RULES.md` says analytics writes are "async/batched". The PRD success metric demands zero data loss on click tracking. As specified, a failed insert loses the click silently.
- **No RFC covers the analytics dashboard UI.** `PRD.md` puts a "Click analytics dashboard" in scope, F5 and F6 describe an analytics page and a timeline chart, and `RULES.md` names React 18 + Vite for it. RFC-002 defines only API endpoints, and no RFC builds the frontend.
- **RFC-002 claims F6 only partly.** F6 includes "date range filtering" (PRD § Analytics: "Filter analytics by date range" for all analytics). RFC-002 gives `from`/`to` only to the timeline endpoint, not to the referrers or countries endpoints.
- **PRD verification was skipped.** There is no `PRD-REVIEW.md`, so the PRD went straight to features and RFCs. The 301/tracking conflict and the open questions above are the kind of issue that stage would have caught.
- There is no drift between the code and the documents, and no RFC was built out of order, because there is no code yet.
