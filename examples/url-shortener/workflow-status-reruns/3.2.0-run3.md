## 3. Inconsistencies

### 3.1 Coverage gaps (trace-check FAILs)

- **F7 (Must have), "REST API for all URL operations", is assigned to no RFC** (FEATURES.md, F7).
  - RFC-001 defines the CRUD endpoints but claims only F1, F2, F4 and F8.
  - No RFC builds rate limiting (100 req/min/IP), even though PRD.md (API), F7, and RULES.md (API Standards, Security) all require it.
  - No RFC covers the `{ data, error, meta }` response envelope or the security headers (helmet/CORS) that RULES.md requires.
- **RFCS.md does not exist.** Without it there is:
  - no Status column to track,
  - no recorded deferral of F14 (OpenAPI docs) or F15 (list URLs),
  - no place to record conflicts or follow-ups.
- **F15 is built but not claimed.** RFC-001 already defines `GET /api/urls - List all URLs (paginated)` (RFC-001, API Endpoints), but its Features line does not list F15 and no acceptance criterion tests it. Either claim F15 in RFC-001 and add a criterion, or remove the endpoint and defer F15 in RFCS.md.

### 3.2 Features claimed but never tested

- **The analytics dashboard UI and the web UI have no RFC.**
  - The PRD asks for a "Click analytics dashboard" (Scope) and a web UI for shortening (User Journeys, "Shorten a URL", step 1).
  - F5 requires a count "displayed on analytics page", F6 a "Chart", and F11 that the "Analytics page shows top 10 referrers".
  - RULES.md specifies React 18 + Vite and Playwright e2e for this UI.
  - RFC-002 claims F5, F6 and F11, but builds only API endpoints. None of its criteria tests a page or chart, and no RFC builds any frontend.
- **RFC-003 claims F13 (malware blocklist) but never tests it.**
  - Its approach calls the blocklist check "Optional" (RFC-003, URL Validation).
  - Its only validation criterion covers format checks (non-HTTP, `data:` URIs).
  - F13's own criterion, "Reject URLs flagged by blocklist service", has no matching criterion. It also depends on PRD open question 2.
- **F4 says deleting a URL also removes its analytics.**
  - RFC-001's delete criterion only covers URL removal and cache invalidation.
  - The cascade that removes clicks is defined in RFC-002 (`ON DELETE CASCADE`), and no criterion there tests it.
- **F2 requires a 404 for expired URLs.** RFC-001 claims F2 but only tests non-existent codes. The expired case is tested in RFC-003. Either move that part of F2 to RFC-003's Features line or note the split.
- **F10's criterion includes automatic cleanup,** which RFC-003 covers. No criterion tests that the Redis redirect cache (RFC-001) is invalidated when the cleanup job hard-deletes rows.

### 3.3 Undeclared RFC dependencies

- **RFC-003 needs RFC-002 but does not declare it.**
  - The cleanup job must "remove expired URLs and their click data" (RFC-003, Expiration and Acceptance Criteria).
  - Click data and the `ON DELETE CASCADE` on `clicks.url_id` only exist once RFC-002 is built (RFC-002, Database Schema).
  - RFC-003 lists only RFC-001 under "Builds upon". Implemented in declared order, the criterion cannot be met or tested.
  - The fix is to add RFC-002 to RFC-003's dependencies, or to move the click-data part of the criterion into RFC-002.
- **RFC-001 builds things that RFC-003 owns.**
  - RFC-001's `POST /api/urls` body already accepts `alias?` and `expiresAt?`, and its schema includes `expires_at` (RFC-001, API Endpoints and Database Schema).
  - RFC-003 says it "extends" the same endpoint with these same fields.
  - The RFCs should say which one owns validating and storing them, or RFC-001's implementation will either half-build RFC-003 or ignore fields its own API documents.
- **The RFCs declare dependencies as "Builds upon" / "Required by", not "Depends on".** trace-check accepted them. Regenerated RFCs should use the standard `Depends on` line.

### 3.4 Self-contradictions within RFCs

- **RFC-001, URL Generation:**
  - It says codes come from "a counter-based approach with base62 encoding for uniqueness" and also from "Collision handling: retry with new random suffix".
  - A counter cannot collide, so the retry step implies random codes.
  - A random suffix would also break the fixed 7-character length that F1 requires.
  - Counter-based codes are also sequential and guessable. With no authentication, anyone can list every link.
- **RFC-003, Custom Aliases:**
  - The approach allows hyphens (`^[a-zA-Z0-9-]{3,30}$`).
  - Its own acceptance criterion, F9, and the PRD all say "alphanumeric".
- **RFC-001 schema:** `is_active BOOLEAN` is defined but nothing in any RFC reads or writes it. RFC-001 says delete "removes", and RFC-003 hard-deletes. Drop the column or define soft delete.

### 3.5 Contradictions between the PRD, RULES.md and the RFCs

- **HTTP 301 clashes with click tracking and expiration.**
  - PRD (Redirection), F2 and RFC-001 all require HTTP 301.
  - Browsers cache 301 responses permanently, so a repeat visitor never reaches the server again. That breaks three things:
    - "Track click metadata on each redirect" (F3) and "Every redirect creates a click record" (RFC-002) fail, and analytics undercount.
    - Expiration (F10) and deletion (F4) have no effect for anyone who already followed the link.
  - A 302/307, or 301 sent with `Cache-Control: no-store`, would resolve this. The choice belongs in the PRD.
- **"Zero data loss on click tracking" clashes with fire-and-forget writes.**
  - The zero-loss target is in PRD.md (Success Metrics).
  - RFC-002 specifies "async fire-and-forget" click inserts, and RULES.md asks for async/batched writes.
  - Fire-and-forget drops clicks whenever a write fails or the process restarts. One of the two has to change, or the RFC needs a durable queue.
- **The PRD gives three different scale targets:**
  - 10,000+ active short URLs (Goals),
  - 10M+ URLs per instance (NFR, Storage),
  - 1,000 redirects/s (NFR, Scalability), which means a synchronous `INSERT` into `clicks` per redirect.
  - None of the RFCs sizes the `clicks` table or plans retention, and retention is still PRD open question 3.
- **The PRD has two latency targets:** "< 100ms p95" (NFRs) and "Average redirect latency < 50ms" (Success Metrics). They do not conflict, but only the first has an acceptance criterion.

### 3.6 RULES.md versions

- **Node.js 20 is past end of life.** RULES.md says "Node.js 20+". Node.js 20 reached end of life on 2026-04-30, so the minimum it allows no longer gets security fixes. Raise the floor to a current LTS line (22 or 24).
- **React 18** is a major version behind the current React release. Confirm whether React 18 is a deliberate choice.
- **"Express.js"** is given without a version, so nothing says whether Express 4 or 5 should be used.
