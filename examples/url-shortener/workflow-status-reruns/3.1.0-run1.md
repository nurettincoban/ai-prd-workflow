## 3. Inconsistencies

**Coverage and index (trace-check FAILs)**
1. **F7 has no RFC.** F7 is "REST API for all URL operations", a Must have, and it includes rate limiting at 100 req/min/IP. RFC-001 defines the endpoints, but its `Features:` line does not list F7. No RFC has rate limiting in its approach or its acceptance criteria. RULES.md (API Standards, Security) and the PRD (API) both require rate limiting, so as things stand nobody would build it.
2. **RFCS.md is missing.** No file records implementation order, statuses or deferrals. `/implement-rfc`, `/review-rfc` and `/manage-changes` keep RFCS.md up to date, so they have nothing to update.
3. **F15 (list URLs) is half covered.** RFC-001 (API Endpoints) defines `GET /api/urls` (paginated), but its `Features:` line does not list F15 and none of its acceptance criteria tests it. Either assign F15 to RFC-001 or drop the endpoint.
4. **F14 (OpenAPI docs at `/docs`) has no RFC and no recorded deferral.** The PRD puts API documentation in week 6, and RFC-003 already reserves the `docs` alias for it.

**Contradictions between artifacts**

5. **Alias character set.** PRD.md (URL Management) and FEATURES.md F9 say "3-30 alphanumeric characters". RFC-003 (Custom Aliases) allows hyphens with `^[a-zA-Z0-9-]{3,30}$`, but its own first acceptance criterion says "alphanumeric". So RFC-003 contradicts itself as well as the PRD.
6. **HTTP 301 vs. tracking every click.** The PRD (Redirection), F2 and RFC-001 specify HTTP 301. Browsers cache a 301 permanently, so repeat visits never reach the server. That conflicts with:
   - F3 / RFC-002, which require a click record for every redirect
   - the PRD success metric "Zero data loss on click tracking"
   - F4 and F10, which say deleted and expired URLs return 404, but a browser that cached the 301 keeps redirecting

   This needs a decision (302/307, or 301 with `Cache-Control: no-store`) before RFC-001 is built.
7. **Delete semantics.** F4 says the analytics data is removed on delete. RFC-002 relies on `ON DELETE CASCADE`, but RFC-001's schema adds an `is_active` column, which suggests a soft delete. A soft delete would leave the click rows in place. RFC-001's acceptance criteria only cover removing the URL and invalidating the cache.
8. **Expiration split across RFCs.** F2 (assigned to RFC-001) requires a 404 for expired URLs, but the expiry check is in RFC-003. RFC-001 already accepts `expiresAt` and has an `expires_at` column, while RFC-003 says it is the one that "extends" `POST /api/urls` with it. The predecessor order is fine; the overlap just needs stating in RFCS.md.
9. **F13 (malware blocklist) is assigned to RFC-003 but not specified.** RFC-003 calls the blocklist check "Optional". Its acceptance criteria only cover URL format and scheme, and nothing meets F13's "Reject URLs flagged by blocklist service".
10. **Date-range filtering.** The PRD (Analytics, "Filter analytics by date range") applies to all analytics. RFC-002 only supports `from`/`to` on the timeline endpoint, not on referrers, countries or the total count.
11. **Code generation in RFC-001 is self-contradictory.** It specifies a counter-based base62 code, which is unique by construction, and also a "retry with new random suffix" when codes collide.
