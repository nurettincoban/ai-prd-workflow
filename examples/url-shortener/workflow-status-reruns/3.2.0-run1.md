## 3. Inconsistencies

### Traceability (trace-check FAILs and coverage gaps)
1. **F7 (Must Have) is in no RFC** (`FEATURES.md` F7). F7 covers the REST API with rate limiting at 100 req/min/IP.
   - No RFC builds the rate-limiting middleware, even though `RULES.md` (API Standards, Security) and the PRD both require it.
   - No acceptance criterion tests consistent error codes or the `{ data, error, meta }` envelope.
2. **The `RFCS.md` index is missing.** No file records RFC status, the order of implementation, or the deferral of F14 and F15.
3. **F15 is partly built but unclaimed.**
   - `RFCs/RFC-001-Core-URL-Shortening.md` (API Endpoints) defines `GET /api/urls - List all URLs (paginated)`.
   - Its Features line omits F15, and no acceptance criterion tests the endpoint.
   - F15 asks for creation date, click count and expiration in the list. Click count needs the `clicks` table from RFC-002, so the endpoint also depends on RFC-002.
4. **F14 (OpenAPI docs at `/docs`) is in no RFC and is not formally deferred.** RFC-003 already reserves the alias `docs`, which assumes a `/docs` route will exist.
5. **PRD.md has no requirement IDs and RULES.md has no rule IDs.** Coverage from PRD to features cannot be checked, and RFCs, reviews and change requests cannot cite rules.

### Undeclared dependencies between RFCs
6. **RFC-003 uses tables from RFC-002 without declaring it.**
   - `RFCs/RFC-003-Custom-Aliases-And-Expiration.md` says the cleanup job deletes "expired URLs and their click data", and one acceptance criterion requires the job to remove "expired URLs and their click data".
   - Click data lives in the `clicks` table, and the cascade delete comes from its `ON DELETE CASCADE`. RFC-002 creates both.
   - RFC-003 lists only `Builds upon: RFC-001`. If RFC-003 is implemented first, that criterion cannot be tested.
   - Fix: add RFC-002 as a predecessor, or move the click-data half of the criterion into RFC-002.
7. **F4's analytics deletion has no owner.**
   - F4 (in RFC-001) requires that "associated analytics data is also removed".
   - RFC-001 cannot do this, because the `clicks` table does not exist until RFC-002. Only the `ON DELETE CASCADE` in RFC-002 satisfies it.
   - No criterion in either RFC tests it.

### RFCs that contradict themselves or claim more than they build
8. **RFC-001 includes RFC-003's scope.**
   - Its `POST /api/urls` body is `{ url, alias?, expiresAt? }`, and its schema has `expires_at`.
   - Aliases and expiration are F9 and F10, which belong to RFC-003. RFC-001 has no criterion for either.
   - It is unclear whether RFC-001 should accept and ignore those fields, or reject them.
9. **RFC-001's code generation contradicts itself.**
   - It says it uses "a counter-based approach with base62 encoding for uniqueness", and also "retry with new random suffix" when a code collides.
   - A counter does not collide, except with custom aliases. Also, counter values only reach 7 characters past 62^6, so either the codes are padded or they are not always 7 characters, while F1 requires 7.
10. **RFC-003's alias rule contradicts its own acceptance criterion and the PRD.**
    - The Technical Approach allows hyphens (`^[a-zA-Z0-9-]{3,30}$`).
    - The acceptance criterion, F9 and the PRD all say "alphanumeric".
11. **RFC-003 claims F13 (blocklist validation) but makes it optional.**
    - Its approach says "Optional: check against a malware blocklist API".
    - No criterion tests the blocklist. The criteria test only URL format and scheme.
    - The PRD's open question about which blocklist service to use is still unanswered.
12. **The analytics UI is claimed but never built.**
    - F5 says "displayed on analytics page", F6 asks for a "Chart showing click distribution", and F11 says "Analytics page shows top 10 referrers". The PRD's View Analytics journey also describes a UI.
    - `RULES.md` names React 18 + Vite for the dashboard.
    - RFC-002 builds only API endpoints, and no RFC builds or tests a frontend. The PRD's "web UI" for shortening has no RFC either.
13. **Date-range filtering is incomplete.** The PRD says "Filter analytics by date range" for all analytics. RFC-002 adds `from`/`to` only to the timeline endpoint, not to the referrers, countries or summary endpoints.

### Drift against the PRD and RULES.md
14. **HTTP 301 conflicts with click tracking, expiration and deletion.**
    - The PRD, F2 and RFC-001 specify a 301 (permanent) redirect. Browsers cache a 301 and stop asking the server.
    - Repeat clicks from a browser are then never recorded, which breaks F3 ("every redirect") and the PRD's "zero data loss on click tracking".
    - Deleted or expired links also keep redirecting for anyone who has visited them before.
    - The PRD should settle this, for example with a 302 or 307, or a 301 with `Cache-Control: no-store`. `/verify-prd` is the step meant to catch this kind of conflict.
15. **RFC-003's expiry check does not cover the Redis cache.**
    - `RULES.md` and RFC-001 make redirects cache-aside through Redis.
    - RFC-003 checks `expires_at` "before redirecting", but it does not say whether the cache entry carries the expiry (a TTL) or is cleared by the cleanup job. A cached expired link could keep redirecting.
16. **Node.js 20 is past end of life.**
    - `RULES.md` (Technology Stack) specifies "Node.js 20+". Node.js 20 reached end of life on 2026-04-30.
    - The floor should be a supported LTS line, such as Node.js 22 or 24.
    - React 18 is a major version behind React 19. Confirm whether it is still the intended choice.
