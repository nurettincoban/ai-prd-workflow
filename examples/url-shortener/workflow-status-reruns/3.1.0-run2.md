## 5. Inconsistencies

### From trace-check (FAIL)

1. **F7 (Must have) is not assigned to any RFC.** F7 is the REST API for all URL operations: CRUD with JSON, error codes and **rate limiting of 100 req/min/IP**. RFC-001 defines the endpoints but lists only F1, F2, F4 and F8 (`RFCs/RFC-001-Core-URL-Shortening.md`, "Features" line). No RFC mentions rate limiting, even though PRD.md ("API" section) and RULES.md ("API Standards" and "Security") require it. As things stand, a Must-have requirement would not be built.
2. **RFCs exist but the RFCS.md index does not.** Without it there is no Status column to track, no implementation order, no record of deferred features, and nowhere to log the conflicts below.

### From trace-check (WARN)

3. PRD.md has no requirement IDs, so coverage from the PRD to the features cannot be checked mechanically.
4. RULES.md rules have no IDs, so RFCs, reviews and change requests cannot cite them.
5. **F14 (OpenAPI docs at /docs) has no RFC**, and no RFCS.md records a deferral. PRD.md lists OpenAPI docs as in scope ("API" section) and plans them for Week 6.
6. **F15 (list URLs) is not credited to any RFC**, but it is actually specified: RFC-001 defines `GET /api/urls - List all URLs (paginated)`. RFC-001's Features line should include F15, or the endpoint should be removed from RFC-001.

### Found by reading the artifacts

7. **Alias character set disagrees.** PRD.md ("URL Management") and FEATURES.md F9 say aliases are "3-30 alphanumeric characters". RFC-003 allows hyphens: `^[a-zA-Z0-9-]{3,30}$`. RFC-003's own first acceptance criterion says "alphanumeric", so the RFC contradicts itself.
8. **HTTP 301 undermines click tracking, deletion and expiry.** PRD.md ("Redirection"), F2 and RFC-001 all specify a permanent 301. Browsers cache 301s, so repeat clicks from the same browser never reach the server. They would not be counted (F3, F5, and "Zero data loss on click tracking" under Success Metrics), and deleted or expired links (F4, F10) would keep redirecting for those users. A 302 or 307, or a 301 with `Cache-Control: no-store`, would avoid this. This is a requirement decision, so it belongs in `/verify-prd`.
9. **"Zero data loss on click tracking" vs fire-and-forget.** PRD.md Success Metrics require zero data loss. RFC-002 ("Click Tracking") records clicks with "async fire-and-forget", and RULES.md ("Performance") says analytics writes should be "async/batched". Fire-and-forget writes are lost whenever the process restarts or the database is unavailable. Either the metric or the design has to change.
10. **RFC-001 and RFC-003 overlap.** RFC-001's `POST /api/urls` body already takes `{ url, alias?, expiresAt? }`, and its schema already has `expires_at`. RFC-003 then says it will "extend" the same endpoint with `alias` and `expiresAt`. It is unclear which RFC owns alias and expiry handling. The likely result is half-built behaviour in RFC-001, or the work being done twice.
11. **Expired URLs: 404 vs automatic cleanup.** RFC-003 hard-deletes expired URLs and their clicks every hour. That fits F10, but it means analytics for an expired campaign are deleted within an hour of expiry. Nobody has agreed to that, and it is tied to open question 3 (analytics retention).
12. **Unused `is_active` column.** RFC-001's schema has `is_active BOOLEAN DEFAULT TRUE`, but no RFC says what sets it or reads it. Deletion is a hard `DELETE` (RFC-001 acceptance criteria).
13. **The analytics dashboard UI has no RFC.** PRD.md (in scope: "Click analytics dashboard"; journey "View Analytics" with a timeline chart) and RULES.md (React 18 + Vite frontend) both expect a web UI. The "Shorten a URL" journey also starts from "the web UI". RFC-002 covers only API endpoints, and no RFC covers any frontend. FEATURES.md does not list the UI as a feature of its own either; F5, F6 and F11 mention an "analytics page" only in their acceptance criteria.
14. **Blocklist check is "optional" in RFC-003.** F13's acceptance criterion requires rejecting blocklisted URLs, and PRD.md's Security NFR requires validation against blocklists. RFC-003 marks the check "Optional", and its acceptance criteria do not test it. This is blocked on open question 2.
15. **Some NFRs have no owner.** No RFC addresses the PRD's 99.9% availability, 1,000 redirects/s per instance or 10M+ URL storage targets, and no RFC sets out how they would be measured. The same goes for the 80% coverage and Playwright e2e requirements in RULES.md. TEST-STRATEGY.md would normally cover these.
