### trace-check warnings

4. RULES.md has no rule IDs, so reviews and change requests cannot cite them.
5. F14 (OpenAPI docs) and F15 (List URLs) are not assigned to any RFC. Without RFCS.md, nothing records whether they were deferred on purpose. F15 is partly built anyway (see item 7).

### RFC against RFC: undeclared predecessors

6. **RFC-003 depends on RFC-002 but declares only RFC-001.** One RFC-003 criterion reads "Cleanup job runs hourly and removes expired URLs **and their click data**". That data lives in the `clicks` table, and its `ON DELETE CASCADE` foreign key is created by RFC-002 (`RFCs/RFC-002-Click-Analytics.md`, Database Schema). RFC-003 says "Builds upon: RFC-001", and RFC-001 says "Required by: RFC-002, RFC-003". If RFC-003 is implemented before RFC-002, that criterion cannot be met or tested. Add RFC-002 as a predecessor, or move the click-data part of the criterion to RFC-002.
7. **RFC-001 builds pieces that belong to features it does not claim.**
   - It lists `GET /api/urls - List all URLs (paginated)`. That is F15, which RFC-001 does not claim and no criterion tests.
   - Its `POST /api/urls` body already includes `alias?` and `expiresAt?`, which belong to RFC-003.
   - Either claim F15 and add a criterion for it, or drop the endpoint. Say which RFC owns the two optional fields.
8. The RFCs use "**Builds upon** / **Required by**" instead of a **Depends on** line. trace-check may therefore not be checking RFC dependencies at all. This is why item 6 passed the mechanical check.

### RFCs that contradict themselves

9. **RFC-001, URL Generation.** It says to "use a counter-based approach … for uniqueness" and then gives "collision handling: retry with new random suffix". A counter cannot collide with itself. The real collision risk is a custom alias from RFC-003 taking a code the counter will produce later. Adding a random suffix would also break the 7-character requirement in F1 and the PRD. Pick one scheme and state how it avoids aliases.
10. **RFC-003, Custom Aliases.** The approach allows hyphens (`^[a-zA-Z0-9-]{3,30}$`). The acceptance criterion, F9 and the PRD all say "alphanumeric". The code and the tests cannot both satisfy this as written.
11. **RFC-001, schema.** The schema has an `is_active` column that nothing uses, while F4 and the DELETE endpoint describe a hard delete. It is unclear whether delete is soft or hard. This matters for F4's rule that the click data is "also removed".

### Features an RFC claims but no criterion tests

12. **F13 (malware blocklist), claimed by RFC-003.** The approach marks the blocklist check as "Optional". The criteria test only format checks (non-HTTP URLs, `data:` URIs) and never test the blocklist. Which blocklist service to use is still an open question in the PRD.
13. **The analytics dashboard UI.** The PRD puts a "Click analytics dashboard" in scope and describes a web UI for shortening (User Journeys). RULES.md names React 18 + Vite and Playwright e2e tests. F5, F6 and F11 refer to an "analytics page" and a "chart". However:
    - No RFC builds any UI.
    - RFC-002's criteria test only API endpoints.
    - No RFC sets up the frontend or the Playwright e2e tests.
14. **F4, "associated analytics data is also removed".** RFC-001's delete criterion tests only the removal and the cache invalidation. RFC-002 adds the cascade but has no criterion for it.
15. **F8 "accessible within 60 seconds" and PRD "deployment in under 5 minutes".** RFC-001's criterion says only "starts the full stack successfully".

### Drift between the PRD and RULES / RFCs

16. **A 301 redirect conflicts with click tracking, expiration and delete.**
    - The PRD, F2 and RFC-001 all specify HTTP 301. Browsers cache a 301 permanently, so a repeat visit never reaches the server.
    - F3 ("every redirect" is tracked) and the PRD's "Zero data loss on click tracking" will then undercount clicks.
    - Expired or deleted links (F4, F10) can keep redirecting from the browser cache.
    - `/verify-prd` should decide this; 302 or 307 is the usual choice when clicks are tracked.
17. **"Zero data loss on click tracking" (PRD, Success Metrics) against fire-and-forget writes.** RFC-002 uses "async fire-and-forget" and RULES.md says "async/batched". Fire-and-forget writes are lost on a crash or a database error. The metric or the approach needs to change.
18. **The Redis cache and expiration.**
    - RULES.md requires a cache-aside Redis cache on redirect.
    - RFC-003 checks `expires_at` "before redirecting" and runs an hourly hard-delete. It does not say whether the check runs on cache hits, or whether the cleanup job evicts cache entries.
    - An expired URL served from Redis would violate F10 and an RFC-003 criterion.
19. **The response envelope.** RULES.md requires a `{ data, error, meta }` envelope on every response. RFC-002's example response shows only `data`.

### Versions in RULES.md

20. **Node.js 20+.** Node.js 20 reached end of life on 2026-04-30. As of today (2026-11-15), the stated minimum no longer gets security fixes. Raise the floor to a supported LTS release (22 or 24).
21. React 18 has been superseded by React 19. The Express major version is not stated. Check both against current support before implementation starts. PostgreSQL 16, Redis 7 and TypeScript 5.x are not flagged here, but confirm the exact Redis 7.x minor version that is still supported.
