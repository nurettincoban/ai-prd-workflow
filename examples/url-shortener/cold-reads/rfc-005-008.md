# Cold read: RFC-005 to RFC-008 (reader: Fable 5.2, clean context, PRD.md + FEATURES.md + RULES.md + one RFC at a time)

## RFC-005 Safe Browsing Blocklist
Guesses:
1. Timeout test ("abort after 2 s → unchecked (fake timers)"): pseudocode calls `AbortSignal.timeout(2000)` directly, which Vitest fake timers probably do not control. Inject the signal/timeout, or the 2 s in AC4 is never exercised.
2. Header fallback ("fall back to the query parameter only if the header is refused"): build-time or runtime? A runtime fallback is a second request, contradicting "not retried" (PERF-5, AC4); "refused" has no defined status; it puts the key in a URL that AC6 does not test.
3. "Normalized destination URL" (AC5) never defined: raw input vs WHATWG `href` give different verdicts.
4. Logger source: `UrlChecker.check(url)` carries no logger; LOG-1 allows only Fastify's pino. Whether the destination goes into the failure log is open (ERR-2).
5. Minor: how `clientVersion` is read in the final image; whether a whitespace-only key counts as empty.
Contradictions: AC7 (no request to any other host) vs SEC-11 (MaxMind download allowed). NFR-8/F21: create can wait up to 2 s against a 200 ms p95; the RFC redefines NFR-8 as "excluding third-party time" by assumption -- needs a PRD decision. F7 UI half: F7 requires the UI to say the URL was not checked; the RFC claims all of F7 but has no UI file or AC.
Weak criteria: AC1 (which checker was picked is not observable, no test seam). AC7 untestable with injected fetch; passes vacuously. AC6 passes by luck; would not catch the query-string fallback.

## RFC-006 Click Rollup and Retention
Guesses:
1. Rollup finality ("once a UTC day has ended no new click can land in it"): `clicked_at` is app clock at request time, insert commits later; a rollup just after midnight misses in-flight or skewed clicks permanently; no grace delay specified. AC2 uses 00:10Z, passes by luck.
2. DETACH then DROP atomicity: not in one transaction → a crash leaves an orphan table never dropped (raw data outlives retention). No `lock_timeout`: DETACH can queue behind inserts and stall redirects (why DATA-6 exists).
3. Aggregate purge `$cutoff` undefined (month- or day-aligned); `LINKSNIP_AGGREGATE_RETENTION_MONTHS` unbounded.
4. Scheduler contract (interface, lock key from RFC-001): do the two jobs share a lock? Does rollup run at startup? If not, startup retention after downtime logs `retention_blocked_not_rolled_up` at error level.
5. Assumes `referrer_host`, `country`, `is_bot` on `clicks`; if `referrer_host` is nullable there, the NOT NULL insert fails.
6. Partition discovery (catalog expression vs name; default partition) unstated.
7. Rollup re-run after a drop: per-day DELETE then INSERT wipes that day's aggregates if its raw partition is gone. Nothing guards against it.
Contradiction: PRIV-3 says aggregates are never purged by the retention job; here the job purges them when the variable is set.
Weak criteria: AC10 vacuous if the known IP never reaches the app; AC9 schedule/lock not testable as written; AC5 "never runs DELETE on clicks" has no observation method; AC4 crash-injection mechanism unspecified.

## RFC-007 Analytics API
Guesses:
1. Date validation layer (AC11): API-2 demands TypeBox querystring schemas, but a date pattern in the schema returns the generic validation code before the handler; `INVALID_RANGE` requires the schema to accept any string. Code for `interval=year` unstated.
2. Bucket cap scope: a defaulted interval is not capped and from/to are unbounded; `from=0001-01-01` gives ~24,000 month buckets.
3. Range-length counting ("≤ 92 days", "401+ days"): inclusive vs difference is an off-by-one at each threshold.
4. `to` before creation with `from` omitted: default `from` > `to` → 400 by the rules, but the edge-case note says zeros.
5. Null host/country sort position and representation (`''` vs NULL → JSON null) unstated.
6. Empty side of the union when the watermark is null; whether the watermark read is inside the snapshot transaction.
7. `totalClicksFor` raw side has no upper `clicked_at` bound (DATA-5) and scans all partitions when watermark is null; `pg` returns bigint/sum as strings, conversion unstated.
8. Minor: `Cache-Control: no-store` on error responses?
Contradictions: AC16 lists 200/400/404/500 schemas, but SEC-9 makes 429 possible on /api/* and API-2 requires every status. F15 says bots excluded "by default"; the RFC makes it unconditional.
Weak criteria: AC10 referrer/country sums "consistent" untestable (top-10 only). AC14 isolation not observable over HTTP. AC15 not checkable for expired links (404).

## RFC-008 Delete and List
Guesses:
1. Auth vs schema validation order (AC7): Fastify validates before the handler, so `limit=0` with no token returns 400, not the 403 SEC-5/AC7 require. Move auth into an earlier hook. Same for delete.
2. `{code}` validation on DELETE: malformed code 400 (API-4) or 404? Order relative to 403?
3. Cursor integrity (AC10): unsigned base64url of a decimal id; tampered cursor that decodes to a number is indistinguishable; ids beyond bigint range (400 vs 500) unstated.
4. `shortUrl` scheme/host source not given.
5. `short_urls_live_idx` "from RFC-001" undefined; if not ordered by id, keyset scan over 10M rows misses NFR-8.
6. Bearer parsing (scheme case, spaces, multiple headers); `expiresAt` null vs omitted.
Contradictions: API-4 gives 404 for expired codes; DELETE returns 204/403 for them. Deleted → 404 but expired → 403 without a token, so the endpoint distinguishes the two. 429 absent from AC14's "every response status". F5/SEC-5 say only unset or empty disables listing; a 1-31 character token now aborts startup.
Weak criteria: AC6 "appears in no log line" depends on redaction configured elsewhere. AC12 not checkable for listed expired links.
